## 范围
**整个项目**（E:\trae-pc\260609work2，130 个 git 跟踪文件，HEAD=c19c536）。

## 你的任务
作为 **Mavis（架构师视角）**，审查 **架构 + 端到端一致性 + 用户体验**：

### 重点审查
1. **架构合理性**：
   - 整体分层（路由 / 服务 / 模型）合理吗？有没有越层调用？
   - 状态机设计（item status 流转）：有没有漏洞？
   - 数据流：项目创建 → 模板选择 → 文件上传 → 复核 → 归档 → 结算书 — 是否有断点？
   - 监控/日志/错误处理：是否可观测？
2. **端到端一致性**：
   - 后端路由名和前端 API 调用是否 1:1 对应
   - 后端 schemas 和前端 types 是否同步
   - 状态字段（status）字符串值是否两端一致
   - 命名（snake_case vs camelCase）是否在边界处转换
3. **用户体验**：
   - Loading / Error / Empty 三态是否都覆盖
   - 操作反馈（toast / 禁用 / loading 状态）是否到位
   - 表单校验（必填 / 长度 / 格式）前后端是否一致
   - 路由错误 / 404 / 500 处理
   - 移动端响应式（不要求完美，但看 Layout 是否合理）
4. **可演化性**：
   - 业务变更（如新增"复核备注"字段）改动面有多大
   - 硬编码常量（端口、文件大小上限、模板种数）是否集中
   - 数据库迁移（alembic？还是直接 create_all？）
5. **Docker 化**：
   - 镜像大小 / 启动速度
   - 卷挂载 / 数据备份策略
   - 健康检查 / 优雅停止
   - 多环境（dev / staging / prod）切换机制

### 输出
**一段 500-1500 字的架构审查报告**，结构：
```
## 架构优点
- ...

## Critical（必须修 — 架构性 bug / 不可逆问题）
- C1: ...（位置: file:line + 问题 + 影响 + 修复建议）
- C2: ...

## Important（建议修 — 一致性 / 体验）
- I1: ...
- I2: ...

## Minor（可选 — 演化 / 文档）
- M1: ...
```

### 不要做
- 不要做修改
- 不要超过 1500 字
- 不要 generic 建议

### 重要：架构师视角
- 关注"系统作为整体"是否合理，不要纠结单文件
- 关注"修改一个地方会不会影响其他"（耦合度）
- 关注"新功能加进来要改多少地方"（内聚度）
- 实事求是，代码好的就明说"这没问题"
