# REQUIREMENT — 项目结算资料管理系统

> 阶段：① 需求（dev-pipeline-mavis）
> 编排者：Mavis
> 日期：2026-06-09
> 模版来源：`项目结算资料交接清单.docx`（25 项标准资料）

---

## 1. 背景

用户（结算岗）当前用 `项目结算资料交接清单.docx` 作为提交资料的纸质模版，列出 25 项标准资料，每项需在工程结束后由施工/监理/建设管理单位准备齐全、签字盖章后移交审核。

痛点：
- **纸质流转**：清单靠邮件/打印传，看不到"齐没齐、谁还差"
- **错漏难追**：缺哪一项、谁没交、什么时候交的，靠人脑记
- **汇总靠人**：所有材料最终要合并成 PDF 结算书，目前手动拼
- **模板僵化**：不同项目增删项时，模版不能"长出"新项

需要一个 **web 工具**，把模版变成可执行、可视化、可追溯的工作流。

## 3. 核心场景

### 场景 A：建项目 + 准备资料

```
1. 结算员打开 http://<server-ip>:8000
2. 点击「新建项目」，填：
   - 项目名称：XX 高速 2024 路面工程
   - 移交日期：2026-06-30
   - 建设管理单位：XX 交投
   - 移交人/接收人
   - 截止日期：2026-07-15
3. 系统自动：
   - 在 projects/<id>/ 下建 25 个子文件夹（01_招标文件/.../25_其它资料/）
   - 在数据库写入 project + 25 个 item
   - 返回项目详情页
4. 结算员把页面发给施工方：把文件拖到对应子文件夹
5. 施工方在文件资源管理器里操作
6. 结算员/监理在 Web 页面看到状态实时更新
```

### 场景 B：人工复核

```
1. 监理打开项目详情页
2. 看到某项状态 = "已上传"（蓝色），文件名列表
3. 鼠标悬停看文件大小、上传时间
4. 点击"打开" → 在新标签页预览 PDF
5. 没问题 → 点"复核通过" → 状态变"已确认"（绿色 ✅）
6. 觉得不全 → 点"驳回" + 写备注 → 状态变"已驳回"（红色）
```

### 场景 C：模版成长

```
1. 项目 A 新增一项："26. BIM 模型文件"
2. 系统提示："是否将此新增项加入标准模版？"
3. 确认 → 写入 master_template.json
4. 之后创建的项目 B/C/D 自动包含这 26 项
```

### 场景 D：生成结算书

```
1. 项目所有项状态 = "已确认"
2. 系统自动把每项的 PDF 转好（如果还是 Word/Excel → 先转 PDF）
3. 生成封面页（项目名/截止日期/总页数/各方签字）
4. 生成目录页（25 项 + 起始页码）
5. 合并全部 PDF → projects/<id>/final/结算书_<name>_<date>.pdf
6. 提供下载链接
```

## 4. 范围边界

### ✅ 范围内

- 局域网部署（FastAPI 起 uvicorn，绑 0.0.0.0）
- 25 项标准资料模版加载与成长
- 项目创建/编辑/删除
- 文件夹监听（watchdog）+ 手动刷新
- 文件名模糊匹配（difflib）
- 4 状态流转：未开始 → 已上传 → 已确认 / 已驳回
- 截止日期倒计时 + 仪表盘
- 非 PDF 文件 → PDF（WPS CLI）
- PDF 合并（pypdf）+ 封面 + 目录
- 基础多用户（无密码，但日志记录 IP）

### ❌ 范围外

- 公网部署 + 鉴权（不实现登录/注册）
- 多租户/角色权限
- 文件版本控制（同名只保留最新）
- 移动端 App（仅 Web 自适应）
- 实时协作/在线编辑
- 邮件/短信通知
- 多语言（仅中文）
- 数据导出到 ERP/财务系统

## 5. 数据模型（高层）

```
Project
  - id (uuid)
  - name (项目名称)
  - handover_date (移交日期)
  - deadline (截止日期)
  - construction_unit (建设管理单位)
  - handover_person (移交人)
  - receiving_unit (接收单位)
  - receiving_person (接收人)
  - created_at
  - status (active / archived)

Item (项目级资料项)
  - id
  - project_id
  - seq (序号)
  - name (资料名称)
  - description (提交说明)
  - pages (页数，用户填)
  - status (pending / uploaded / confirmed / rejected)
  - rejected_note (驳回备注)
  - confirmed_at

File (项目级文件)
  - id
  - item_id
  - filename
  - filepath
  - filesize
  - uploaded_at
  - is_pdf
  - pdf_path (转码后)

Template
  - master_template.json (全局模版，可成长)
  - version
```

## 6. 关键决策（已与用户确认）

| 维度 | 选择 | 理由 |
|------|------|------|
| 技术栈 | **Python FastAPI + React + SQLite** | python-docx 解析 Word 强，watchdog 稳，pypdf 合并快 |
| 部署 | 局域网多人 | 绑 0.0.0.0，FastAPI 多 worker |
| 文件监听 | 混合（实时 + 手动刷新） | watchdog 主，失败兜底手动 |
| PDF 引擎 | WPS Office | 用户本机已装，`wps --convert-to pdf` 走 CLI |
| 模版演化 | 项目新增项可选推送到全局模版 | 用户选择是否推广 |

## 7. 风险 & 缓解

| 风险 | 缓解 |
|------|------|
| WPS CLI 不在 PATH | 启动时探测常见路径 + 提示用户 |
| 局域网 IP 变动 | 启动时打印"服务地址: http://192.168.x.x:8000" |
| 多个用户同时操作 | SQLite WAL 模式 + 行级锁 |
| 大文件（>100MB）转 PDF 慢 | 异步任务队列（FastAPI BackgroundTasks） |
| 中文文件名编码 | 全程 UTF-8，路径用 `pathlib` |
| Word 转 PDF 排版错位 | 转完用 pdfinfo 校验页数，不对则告警 |
| 模版被误改 | master_template.json 入 git，可回滚 |
